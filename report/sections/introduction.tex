\subsection{Background and motivation}
\IEEEPARstart{C}{apture-the-Flag} (CTF) challenges have become one of the
primary experiential instruments used to teach offensive and
defensive cybersecurity skills at both undergraduate and postgraduate
level~\cite{KeesPetrelli,Vykopal}. They reward the hands-on application
of theoretical knowledge in the form of a concrete, gated artefact
(the flag), and in so doing they address a long-standing concern in
engineering education that purely lecture-based instruction fails to
transfer to authentic practice~\cite{Dewey1938,kolb1984}. Durham
University's own COMP2211 Networks and Systems module distributes a
single virtual machine image containing a fixed catalogue of
Jeopardy-style challenges; while the exercise exposes students to a
breadth of problem types, the shared image introduces three pedagogical
and integrity weaknesses that this project addresses directly.

First, the vulnerability surface is fixed across the cohort, so an
exploit methodology that works for one student transfers to every
other student verbatim --- the per-user flags personalise the
\emph{string} that proves a solve, but they do not personalise the
\emph{path} that produces it, so a single write-up still solves the
cohort. Second, the personalisation that does exist is randomised
once at build time and baked into the VM image, with no mechanism to
rotate flag space across years or salt deployments without re-issuing
images. Third, the challenges predate the widespread availability of
capable large language models; uniform problem structures that
closely resemble the public exploit write-ups on which those models
are trained are readily solvable by prompting
alone~\cite{ji2025}. Beyond integrity, the existing module also skews
toward classical vulnerability classes (SQL injection, path
traversal, weak authentication) and toward legacy stacks (PHP with
raw \texttt{mysqli}), which under-represent both the vulnerability
landscape that graduates will encounter in industry and the modern
framework ecosystem (TypeScript single-page applications, queue-driven
microservices, templated server-side rendering, compiled-language web
servers) in which those vulnerabilities manifest in subtly different
ways.

\subsection{Research question and aims}

The research question guiding this project is:
\begin{quote}
\textit{``\textbf{How can modern web application vulnerabilities be authentically
modelled and pedagogically structured within Capture-the-Flag
environments to enhance learning outcomes in cybersecurity education?}''}
\end{quote}

Concretely, the project pursues three co-dependent aims. The first is
\textit{coverage}: to design a suite of web exploitation challenges
that spans both the established vulnerability classes students must
know (broken access control, cryptographic failures, injection,
authentication failures) and the under-represented modern classes
(server-side template injection, server-side request forgery against
cloud metadata, insecure deserialisation) that existing educational
platforms largely omit~\cite{Sasiwanit}. The second is
\textit{integrity}: to construct a shared personalisation layer that
makes flag sharing attributable and makes LLM-generated flags
structurally invalid, without resorting to the full infrastructural
cost of per-student environment randomisation~\cite{chothia2023}.
The third is \textit{engineering rigour}: to package each challenge
as a portable, self-contained artefact whose intended exploit path
is verified by automated end-to-end tests rather than by instructor
inspection alone.

\subsubsection{Deliverables}
The project deliverables are organised into three tiers of increasing
engineering scope, summarised in Table~\ref{tab:deliverables}: a
\textit{Basic} baseline that establishes the
challenge-as-container model on a small set of CTFs; an
\textit{Intermediate} tier that extends the suite to its full
nine-challenge, eight-OWASP-category footprint with multi-stage
chains; and an \textit{Advanced} tier that wraps the suite in a
three-layer test apparatus, continuous integration, and a structured
LLM-and-human evaluation. Tier here denotes \emph{deliverable
scope} rather than per-CTF challenge difficulty; the
challenge-difficulty axis (Easy/Medium/Hard) is treated as an
orthogonal property of individual CTFs and is set out in
Table~\ref{tab:suite-summary}. Collectively, the deliverables
address a gap identified in the literature: existing educational
CTF platforms typically offer narrow vulnerability coverage limited
to classical flaws such as SQL injection and
XSS~\cite{Sasiwanit}, lack per-user flag personalisation beyond
simple randomisation, and do not account for the ease with which
LLMs can solve uniform, well-documented challenges~\cite{ji2025}.
This project targets all three shortcomings within a single
web-specific, graded coursework context.

\subsubsection{Measures of success}

\paragraph{\textbf{Basic}} The initial group of CTF challenges deploy
on a clean machine with no manual configuration beyond providing a
student identifier; each intended exploit path yields a byte-correct
per-user flag; non-exploitable features behave realistically
alongside the deliberate vulnerability; and the per-deployment salt
plus HMAC-SHA256 derivation produces flags that change between
deployments without challenge-source modification.

\paragraph{\textbf{Intermediate}} The suite extends to nine
challenges spanning eight of the ten 2021 OWASP categories and nine
distinct technology stacks. Multi-stage and multi-flag chains are
solvable end-to-end through their intended paths without external
knowledge; each stage exposes a breadcrumb (CHANGELOG entry,
\texttt{/health} metadata, in-page hint) that surfaces the material
the next stage requires. The standardised Post-Design Audit record
per challenge confirms that no trivial unintended solution bypasses
the intended chain.

\paragraph{\textbf{Advanced}} Per-challenge unit and integration
tests, the end-to-end exploit harness, and the nine-job CI matrix
all run green across the corpus on every push to \texttt{main}.
The LLM solvability harness is committed under
\texttt{Evaluation/llm/} with a fail-closed sandbox, per-CTF
doc packs, expected-flag map, and a five-condition run matrix,
ready for deferred execution under a budget-bounded run; the
byte-match success criterion ensures any methodologically
correct but hallucinated flag would be recorded as a categorical
failure. The human walkthrough is delivered to a Durham CS
sample under a pre-committed protocol, with outcome,
time-to-flag, AI-tool use, confidence shift, and enjoyment and
learning Likerts collected for analysis.

\subsection{Achievements}

The principal outcomes of the project are as follows.

\textbf{A nine-challenge suite.} Nine CTFs were designed,
implemented, and deployed, spanning insecure session handling
(CTF1), weak JWT secret disclosure via proof-of-work (CTF2),
multi-stage SQL injection and AES-CBC decryption in an HR system
(CTF3), DOM-based XSS escalated through an automated admin bot
(CTF4), server-side template injection with WAF bypass in a Flask
CMS (CTF5), server-side request forgery traversing simulated cloud
metadata and internal Redis (CTF6), insecure deserialisation via
\texttt{node-serialize@0.0.4} (CTF7), an editorial system chaining
IDOR, client-side admin-guard bypass, and OS command injection on a
diagnostic endpoint (CTF8), and a six-stage Spring Boot enterprise
chain combining actuator exposure, traversal, JWT algorithm
confusion, blind Boolean SQLi, hybrid RSA-512 + AES-GCM crypto, and
a logfile-based password leak (CTF9). The suite covers eight of the
ten 2021 OWASP categories and implements three distinct injection
sub-types. No two challenges share the same primary technology stack.

\textbf{A shared personalisation layer.} A reusable generation
framework produces per-user credentials and flags for each challenge
from a single cohort roster. Flags are derived deterministically via
HMAC-SHA256 over a per-deployment, per-challenge, per-flag-slot salt,
embed the recipient's username into the flag string, and cannot be
reconstructed by an LLM that does not hold the secret salt. The
resulting flag space changes between deployments, invalidating any
prior write-ups without modifying the challenge code.

\textbf{Portable, reproducible containerisation.} Every challenge is
packaged as a Docker Compose stack with no student data or flag
content baked into the images. Flags and credentials are mounted as
read-only volumes at startup, so a new cohort can be onboarded by
re-running the generator and restarting the stacks, with no
modification of challenge source code.

\textbf{Objective ground-truth testing across three layers.}
Every challenge ships first-party unit and integration tests in
its native framework (Jest with Supertest, PHPUnit, pytest, cargo
test, Go testing, JUnit~5), driven by a single cross-stack runner
at \texttt{CTFs/run-all-tests.sh}. A Python end-to-end exploit
script per challenge then drives the full intended attack chain
against a running stack and asserts the presence of the student's
personalised flag in the application's response. The same per-CTF
commands run in nine parallel CI jobs
(\texttt{.github/workflows/tests.yml}) on every push and pull
request, gating ``contracts green across the corpus.'' These
layers serve both as regression tests during development and as
an objective baseline for the evaluation of automated solvers.

\textbf{Dual evaluation.} The suite is evaluated through a
triangulation of sources: the automated exploit scripts provide
solvability ground truth, an LLM-assisted solvability trial assesses
resistance to automated solving, and a structured human walkthrough
elicits qualitative feedback from participants across a range of
skill levels. Section~\ref{sec:results} presents the results of each
track and discusses the implications for the pedagogical and
integrity claims made in the design.
